# Codex Rules

本文件为 append-only 规则账本，基线来源为 `docs/architecture/init.md` 的 `R-001` 至 `R-115`，后续规则按追加方式扩展到当前版本。

## 文档与治理

- `R-001`：每个独立 Task 完成后必须清理上下文，只保留 ADR 引用和任务结论。
- `R-002`：用户输入中涉及实现的约束必须抽取并永久固化。
- `R-003`：规则库维护机制本身也受规则约束，不能删除或篡改。
- `R-004`：初始部署完成后必须提醒补齐其他环境配置。
- `R-005`：编码前必须先确认前端技术栈。
- `R-006`：任务执行必须按固定顺序优先读文档，而不是依赖 prompt 和记忆。
- `R-007`：跨步骤、跨前后端、跨领域任务必须先建或更新执行计划。
- `R-008`：新的需求或方案文档入库后，必须先保存到 `docs/references/` 再拆分落地。
- `R-009`：长期规则、边界和设计方向必须进入追加式历史账本。
- `R-010`：可复用规则必须落到文档、测试或 lint。
- `R-011`：`AGENTS.md` 必须保持简短，长期知识放入 `docs/`。
- `R-012`：大模块默认交付流程是完成记录、commit、tag、tag 回写完成记录。
- `R-013`：验证前后必须切换上下文，隔离实现态和验证态。
- `R-014`：遵循低 token 原则，先搜再读且只读最小必要范围。
- `R-062`：执行时必须保留全部需求原文和人类提供的规范原文。

## 架构与工程硬约束

- `R-015`：前后端必须可独立构建和部署。
- `R-016`：前端固定 Vue 3 + JavaScript + CSS，后端固定 Java 8 + Spring Boot 2.x。
- `R-017`：文件统一 UTF-8/LF，运行与构建路径兼容 amd64 和 arm64。
- `R-018`：前端负责编排与预校验，后端是规则、编排、执行、持久化与审计的权威边界。
- `R-019`：关键领域判断不能长期留在前端状态里，后端必须重校验。
- `R-020`：新的跨域行为必须经过后端 `controller -> service` 实际分层进入；当前 `application` 仅作为承载这些入站与编排代码的包域，不单独构成一层。
- `R-021`：后端至少具备接口层、dto、service、logic/impl、entity、dao/mapper、vo 等分层。
- `R-022`：后端包结构必须是“领域目录 + 分层子目录”。
- `R-061`：项目必须前后端分离、支持 ARM，前端轻量、后端可重且强制分层。
- `R-068`：保持高内聚低耦合，跨域通过 Service DTO 交互，禁止 Entity 直接跨服务传输。

## 前端与页面

- `R-023`：页面必须按上下文、当前任务、关键输入、运行状态、结果、历史、下一步的顺序组织。
- `R-024`：优先展示摘要、结论和建议，JSON 仅做下钻。
- `R-025`：多个核心流程不能继续堆在同一长页面中。
- `R-026`：常驻页面承载主流程，弹窗和抽屉只做编辑、确认、告警。
- `R-027`：页面应尽量利用完整视口，避免卡片套卡片。
- `R-028`：已交付后端能力必须在 operator 页面可见。
- `R-029`：历史 spec 或已完成计划中定义的页面能力未经人工批准不能移除。
- `R-030`：开发门户和业务主路径必须分离。

## 持久化、历史、导出、审计

- `R-031`：MySQL 是后续主持久化方向。
- `R-032`：浏览器本地状态不能作为历史查询或导出的唯一事实来源。
- `R-033`：历史对象必须支持后端查询、筛选、分页和导出。
- `R-034`：配置、结果、历史、导出、审计之间必须有可追溯关联键。
- `R-035`：密码、令牌等敏感信息禁止明文落库。
- `R-036`：完成结果是不可变证据，只允许注释、标签、归档、软删除类元数据控制。
- `R-037`：导出必须基于后端快照或可复现查询。
- `R-038`：历史默认永久保留，增长问题通过观测、分页、过滤解决。
- `R-039`：压测路径必须覆盖关键状态流转日志，且日志不得泄露敏感字段。

## 可靠性与安全

- `R-040`：结项前至少执行知识检查、后端测试、前端构建和文档代码一致性检查。
- `R-041`：HTTP handler 失败时必须返回明确 JSON 错误。
- `R-042`：相同输入应尽量产生确定性的 workflow 输出。
- `R-043`：MySQL 三种 repository mode 必须保持同样的 workflow 和 history 契约。
- `R-044`：影响 operator 的运行假设必须落到测试、日志、配置或文档。
- `R-045`：当前边界不执行任意 SQL，未来接入默认只读优先且影子测试必须可审计。
- `R-046`：transport 边界必须做 request 校验，tenant 身份必须显式化。
- `R-047`：每个新的外部 connector 都必须记录访问范围和安全边界。

## 产品级与冲突确认

- `R-048`：目标架构不能被当成已实现事实，已交付行为以当前实现文档为准。
- `R-049`：涉及删规则、改边界、废弃主存储或变更契约且有兼容风险的需求必须先记录影响并人工确认。
- `R-050`：冲突记录至少包含受影响范围、收益、破坏面、推荐方案和备选方案。
- `R-069`：项目总原则是轻前端、权威后端、MySQL 主持久化、后端负责历史导出审计、页面按任务流组织、规则必须文档化或工具化。

## 技术选型确认

- `R-051`：代码版本管理采用 GitHub Flow。
- `R-052`：开源协议采用 Apache License 2.0。
- `R-053`：文件编码必须为 UTF-8，行尾必须为 LF。
- `R-054`：前端技术栈采用 Element Plus + 自研组件。
- `R-055`：暂不引入数据库迁移工具，达到阈值时再评估 Flyway。
- `R-056`：API 版本控制以 `Accept-Version` Header 为主，URL 路径和参数为辅。
- `R-057`：错误码全局统一，系统级 `10000-19999`，业务级 `20000-29999`，再按服务域细分。
- `R-058`：Git 提交规范采用 Conventional Commits。
- `R-059`：暂不要求版权头模板。
- `R-060`：流程主要节点必须打印有效日志。
- `R-063`：前端样式方案是 Element Plus + 自研。

## 后端实现

- `R-064`：流程日志至少包含操作类型、实体标识、耗时和结果状态。
- `R-065`：数据访问层必须使用 MyBatis XML，禁止复杂 SQL 注解化。
- `R-066`：多环境配置必须通过 `application-{profile}.yml` 区分，禁止硬编码。

## 等保合规

- `R-111`：所有用户操作必须经过后端身份鉴别，管理员与普通用户权限分离。
- `R-112`：必须基于租户 ID 做访问控制与数据隔离，禁止越权查询。
- `R-113`：所有 SQL 操作、登录登出、权限变更必须进入审计日志，保留不少于 180 天且不可改删。
- `R-114`：数据库密码、API 密钥等敏感配置必须加密存储，禁止明文落库。
- `R-115`：MySQL 必须具备主从复制和定期全量备份，满足 `RPO < 1小时`、`RTO < 4小时` 且备份加密。

## 验证规则体系（R-116 至 R-143）

### 维度1：阶段质量门禁（Phase Gate）

#### R-116 阶段入口验证

- 触发时机：新阶段启动前
- 检查清单：
  1. 上一阶段所有阻塞 Issue 状态 = 已关闭
  2. 规则库已追加本阶段新规则
  3. ADR 状态与本阶段技术决策匹配
  4. 执行计划文档已创建/更新
- 通过标准：4 项全部通过
- 失败处置：禁止进入下一阶段，返回未就绪项清单
- 关联规则：`R-007`, `R-012`

#### R-117 阶段交付质量门禁

- 触发时机：阶段结项时
- 检查清单：
  1. 该阶段定义的 100% 检查项已执行（见各阶段检查表）
  2. SonarQube 零 Blocker/Critical
  3. 单元覆盖率达到阈值（阶段 0：80%，阶段 1+：85%）
  4. 所有服务 `mvn clean install` 通过
  5. 前端 `npm run build` + `npm run lint` 通过
  6. 数据库脚本可执行
  7. `lint-repository-knowledge.js` 通过
- 通过标准：7 项全部通过
- 失败处置：标记阶段状态为“待修复”，输出阻塞清单
- 关联规则：`R-040`, `R-012`

#### R-118 渐进等保验证

- 触发时机：每阶段结项时
- 检查清单：重新验证 `R-111` 至 `R-115` 对应的实现，包括：
  1. 身份鉴别入口未被删除或绕过
  2. 访问控制逻辑未被弱化
  3. 审计日志表结构与保留策略未变更
  4. 敏感字段加密机制未退化
  5. 备份策略提示未删除
- 通过标准：5 项全部通过
- 失败处置：标记为合规退化，必须修复后重新验证
- 关联规则：`R-111`, `R-112`, `R-113`, `R-114`, `R-115`

### 维度2：任务级即时验证（Task Validation）

#### R-119 代码生成即时编译

- 触发时机：每个 Task 代码生成后
- 检查清单：
  1. 后端执行 `mvn clean compile` 或前端执行 `npm run build`
  2. 无编译错误
  3. 无新增 deprecation warning（除非 ADR 允许）
- 通过标准：3 项全部通过
- 失败处置：不进入下一 Task，必须修复编译错误
- 关联规则：`R-021`, `R-022`

#### R-120 分层结构回归

- 触发时机：任何涉及包结构调整的 Task 后
- 检查清单：
  1. 目录树符合“领域目录 + 分层子目录”
  2. 无顶层扁平 `controller/service` 目录（`QV-001` 复现检查）
  3. 领域层无 Spring 注解
  4. 包名与目录结构一致
- 通过标准：4 项全部通过
- 失败处置：立即重构，禁止提交
- 关联规则：`R-021`, `R-022`, `QV-001`

#### R-121 接口契约符合度

- 触发时机：新增/修改接口后
- 检查清单：
  1. 输入字段与契约文档一致（名称/类型/必填/长度）
  2. 输出字段与契约文档一致
  3. 边界条件处理（空值/超时/超长/越界）
  4. 错误码在 `ErrorCodeConstants` 中定义
- 通过标准：4 项全部通过
- 失败处置：更新契约文档或修改代码，保持双向一致
- 关联规则：`R-041`, `R-057`

#### R-122 MyBatis XML验证

- 触发时机：涉及数据库操作的 Task 后
- 检查清单：
  1. SQL 写在 XML 中，非注解
  2. Mapper 接口与 XML `namespace` 一致
  3. 参数使用 `#{}` 预编译，禁止 `${}` 拼接（防注入）
  4. 复杂查询有 EXPLAIN 计划注释
- 通过标准：4 项全部通过
- 失败处置：重构为 XML 方式
- 关联规则：`R-065`, `R-045`

#### R-123 流程节点日志验证

- 触发时机：涉及业务逻辑的 Task 后
- 检查清单：
  1. 主要节点（入口/出口/异常/状态变更）有日志
  2. 日志包含操作类型、实体标识、耗时、结果状态
  3. 无敏感信息明文打印
- 通过标准：抽查通过
- 失败处置：补充日志或脱敏处理
- 关联规则：`R-060`, `R-064`, `R-039`

#### R-124 前端三件套验证

- 触发时机：前端代码修改后
- 检查清单：
  1. `npm install` 通过
  2. `npm run build` 通过
  3. `npm run lint` 通过（0 error）
  4. 路由/国际化/主题变量文件未被误删
- 通过标准：4 项全部通过
- 失败处置：修复后重新 build
- 关联规则：`R-088`, `R-089`, `R-090`, `R-091`, `R-092`, `R-093`, `R-094`, `R-095`, `R-096`, `R-097`, `R-098`

### 维度3：修复回归验证（Fix Regression）

#### R-125 阻塞问题修复回归

- 触发时机：阻塞问题（如 `QV-xxx`）修复后
- 检查清单：
  1. 重新执行该问题的完整验证流程
  2. 原验证报告中的检查项 100% 通过
  3. 修复未引入新问题（Git diff 检查）
  4. 更新验证报告状态为“已修复”
- 通过标准：4 项全部通过
- 失败处置：继续修复，禁止进入下一阶段
- 关联规则：`R-040`, `R-128`

#### R-126 跨服务影响验证

- 触发时机：修改 common 模块或接口契约后
- 检查清单：
  1. 所有消费该 common 的服务编译通过
  2. 接口变更方已通知消费方
  3. 契约测试用例更新并通过
- 通过标准：3 项全部通过
- 失败处置：协调消费方同步修改或保持向后兼容
- 关联规则：`R-020`, `R-068`

#### R-127 性能基线回归

- 触发时机：涉及解析/路由/执行的优化或重构后
- 检查清单：
  1. JMH 基准测试通过
  2. P99 延迟不超过该阶段基线（阶段 1：50ms）
  3. 内存占用不超过基线（阶段 1：2GB）
- 通过标准：3 项全部通过
- 失败处置：回滚或优化，禁止合并
- 关联规则：`R-003`

### 维度4：环境与配置验证（Environment）

#### R-128 多环境配置隔离

- 触发时机：修改 `application-*.yml` 后
- 检查清单：
  1. `dev/test/prod` 三个文件存在且非空
  2. 各环境数据库连接指向不同实例
  3. 生产配置 `auth.enabled=true`，`dev` 可为 `false` 但必须有注释说明
  4. 敏感配置（密码）使用环境变量或加密，禁止明文
- 通过标准：4 项全部通过
- 失败处置：重构配置，敏感信息轮换
- 关联规则：`R-066`, `R-114`

#### R-129 数据库脚本同步

- 触发时机：Entity 或表结构变更后
- 检查清单：

## Kafka专项开发模式

#### R-144 Kafka本地开发抽象模式

- 触发时机：Codex 识别到任务涉及 Kafka 生产者、消费者、Topic、消息发送、事件监听等任何 Kafka 相关功能时。
- 执行动作：必须自动按本规则实现 Kafka 抽象层与环境切换，禁止直接要求本地启动 Kafka 服务作为开发前置条件。

##### 核心原则

1. 本地开发环境不强制部署 Kafka，但 Kafka 功能逻辑必须可验证，可通过模拟、数据库或接口方式完成。
2. 生产环境配置必须可无缝切换至真实 Kafka，不允许本地模拟方案侵入生产路径。
3. 代码结构必须预留 Kafka 接入点，业务代码禁止直接依赖具体消息中间件实现。

##### 实现模式（三选一，按场景优先级）

1. 模式A：数据库模拟模式（默认优先）
   - 适用场景：审计日志、异步通知、状态流转等可持久化消息。
   - 实现要求：
     - 创建表 `kafka_message_queue`（或领域相关表名），字段至少包含：
       - `id`：`BIGINT` 自增
       - `topic`：`VARCHAR(128)`，模拟 Kafka Topic
       - `partition_key`：`VARCHAR(128)`，分区键
       - `message_body`：`TEXT`，JSON 格式消息体
       - `headers`：`TEXT`，JSON 格式消息头
       - `status`：`ENUM('PENDING','SENT','CONSUMED','FAILED')`
       - `retry_count`：`INT DEFAULT 0`
       - `created_at`：`TIMESTAMP`
       - `consumed_at`：`TIMESTAMP`
       - `error_log`：`TEXT`
     - 生产者统一通过 `KafkaProducerService.send(topic, key, message, headers)` 或等价抽象接口发送。
     - `dev` 环境写入消息表并将 `status='PENDING'`。
     - `prod` 环境通过配置切换为真实 Kafka Producer 发送。
     - 消费者统一通过 `KafkaConsumerService.poll(topic, batchSize)` 或等价抽象接口消费。
     - `dev` 环境从消息表中轮询 `status='PENDING'` 数据模拟拉取。
     - `prod` 环境切换为 `@KafkaListener` 或等价 Kafka 消费机制。
     - 必须提供每 5 秒扫描待消费消息的调度任务，消费成功更新为 `CONSUMED`，失败则 `retry_count + 1`，超过 3 次标记为 `FAILED`。
     - 必须提供管理接口：
       - `POST /api/governance/admin/messages/retry`：重试 `FAILED` 消息
       - `GET /api/governance/admin/messages/stats`：查询消息统计
2. 模式B：接口转发模式
   - 适用场景：消息需要与外部系统交互，例如第三方平台回调或转发。
   - 实现要求：
     - `dev` 环境由生产者调用 MockServer 或本地 HTTP 接口。
     - Mock 响应必须可预设，以验证业务处理逻辑。
     - `prod` 环境切换为真实外部接口地址。
3. 模式C：内存队列模式
   - 适用场景：纯单元测试。
   - 实现要求：
     - 使用 `ConcurrentLinkedQueue` 或等价内存队列模拟 Topic。
     - 测试用例必须验证入队、出队与监听逻辑。
     - 禁止用于集成测试或本地开发验证。

##### 配置切换机制（强制）

- `application-dev.yml`

```yaml
messaging:
  mode: DATABASE
  kafka:
    enabled: false
    bootstrap-servers: localhost:9092
  database:
    enabled: true
    poll-interval: 5000
    max-retry: 3
```

- `application-prod.yml`

```yaml
messaging:
  mode: KAFKA
  kafka:
    enabled: true
    bootstrap-servers: kafka-cluster:9092
    producer:
      acks: all
      retries: 3
    consumer:
      group-id: sqlforge-group
      auto-offset-reset: earliest
  database:
    enabled: false
```

##### 代码结构要求

1. 抽象接口层固定为 `domain/messaging/`
   - `MessageProducer.java`：`send(topic, key, message, headers)`
   - `MessageConsumer.java`：`poll(topic, batchSize)` / `listen(topic, handler)`
   - 禁止业务代码直接依赖 `KafkaTemplate` 或任何具体消息实现。
2. 实现层固定为 `infrastructure/messaging/`
   - `DatabaseMessageProducer.java` / `DatabaseMessageConsumer.java`
   - `KafkaMessageProducer.java` / `KafkaMessageConsumer.java`
   - `MockMessageProducer.java` / `MockMessageConsumer.java`
3. 工厂与配置层固定在 `config/`
   - `MessagingConfig.java`：根据 `messaging.mode` 创建对应 Bean
   - 使用 `@ConditionalOnProperty` 做环境切换

##### 验证要求

1. 本地开发验证（无需 Kafka 运行）
   - 调用业务接口触发消息发送。
   - 查询消息表确认写入成功。
   - 等待 5 秒或手动调用 `/api/governance/admin/messages/retry`，确认消息进入消费流程。
   - 检查业务结果，例如审计日志或状态表更新。
2. 单元测试验证
   - 使用 `@ActiveProfiles("test")` 且 `messaging.mode=MOCK`。
   - 验证消息入队后业务监听器被调用。
   - 验证异常场景的重试逻辑。

##### 文档要求

1. 每次实现 Kafka 相关功能时，必须同步更新 `docs/architecture/messaging-abstraction.md`，说明当前采用的模式、切换方式与约束边界。
2. 接口契约文档必须标注 Topic 名称、消息格式与消费顺序要求。

##### 关联规则

- `R-066`：多环境配置隔离
- `R-068`：高内聚低耦合
- `R-121`：接口契约符合度
- `R-128`：环境配置验证

- `blocked` 任务必须包含 `Next action:`、`Escalation:`、`Human decision:` 与 `INBOX ref:`；`in_review` 任务必须包含 `Review reason:`、`Human decision:` 与 `INBOX ref:`。
- 若 `blocked` / `in_review` 缺少升级链记录，任务不得伪装成可自动继续、可关闭或可回退为普通执行态；必须先补齐记录。
- `todo` / `in_progress` 任务不得保留未决人工判断、升级链字段或显式等待人类处理的标记；出现此类内容时，必须升级为 `blocked` 或 `in_review`。
- 不得额外创建 JSON、YAML 或其他机器状态文件追踪任务状态；`.agent/config.json` 仅用于机器参数，不记录任务状态。

### R-157 任务关闭与单任务提交

- 每个完成任务必须按“实现 -> 自审 -> 验证 -> 文档同步 -> 台账回写 -> 归档 -> 单任务 commit”的顺序关闭。
- 一个已验证任务对应一个 commit，commit subject 必须同时满足 Conventional Commits 与 task id 约束。
- 只能 stage 当前任务相关文件，禁止 `git add .`、`git add -A`、`git commit -a`。
- 若 commit 未成功，任务不得视为完成。

### R-158 INBOX 人工决策入口

- `INBOX.md` 只记录仍需人类判断、批准、优先级排序或任务塑形的问题。
- `INBOX.md` 条目必须使用稳定 ID（如 `INBOX-001`），并记录 `Status:`、`Needed decision:`，以及 `Task refs:` / `Plan refs:` 之一。
- 已在任务日志中完整记录的失败或确定性工程事项，不得重复记入 INBOX。
- 若问题已升级到 `INBOX.md`，对应任务必须通过 `INBOX ref:` 回指该条目，且该条目必须在 `Task refs:` 中列出对应 task id；`Plan refs:` 只用于补充计划背景或尚未形成任务的事项。若仅保留在任务日志，必须写明 `INBOX ref: task-log-only: <reason>`。
- 未经人类确认，不得直接把 INBOX 条目转为实现任务。

### R-159 根 Git 边界与嵌套仓阻断

- 仓库根目录是唯一规范 Git 边界。
- 若发现 nested `.git`、Git 拓扑漂移或冲突状态，foreman 必须暂停，等待人类确认处理方式。
- 根 Git 边界无效时，不得继续执行任务关闭流程。

### R-160 任务审计脚本强制执行

- pre-closeout 必须执行 `python3 scripts/task_audit.py --check --phase pre-closeout`，单任务 commit 完成后必须立即执行 `python3 scripts/task_audit.py --check --phase post-closeout`。
- 审计脚本至少检查：活动台账不得含 done、任务 ID 不重复、`tasks-done.md` 最新归档顺序正确、`blocked` / `in_review` 任务含人类决策元数据与 `INBOX ref:`、`todo` / `in_progress` 不得静默保留待人类处理标记、完成任务 commit subject 按阶段满足 Git history 可追溯要求。
- 若 task audit 失败，必须先修复台账、补齐升级链记录或 Git 追踪问题，再继续关闭流程；禁止把“需人类判断”的任务伪装成可自动继续状态。

### R-161 外部规则迁移替换约束

- 从其他项目迁移 harness engineering 规则时，只允许迁移治理思想、流程结构和验证口径。
- 其他项目专属的服务名、模块边界、HTTP 路由、端口、运行时拓扑、测试矩阵和 artifact 名称不得直接作为 SQLForge 事实沿用。
- 迁移结果必须显式替换为 SQLForge 当前仓库事实，或明确标记为“仅迁移思想、不迁移实现语义”。

### R-162 治理批次闭口一致性

- 文档/规则/计划治理批次结束时，必须同时闭口：
  - `tasks-done.md`
  - `docs/quality/validation-log.md`
  - 对应复盘文档
  - git 提交历史
- 不允许只写验证日志或只写复盘，而不归档任务或不形成提交记录。

### R-163 阶段前置条件显式矩阵

- 主执行计划之外，必须维护可直接检查的阶段前置条件矩阵。
- 矩阵至少覆盖：
  - 输入文档
  - 依赖 ADR
  - 规则编号
  - 验证规则
  - 人工确认点

### R-164 Task 扩展治理字段

- 核心 10 字段不足以表达严格治理要求时，必须追加维护 Task 扩展治理字段矩阵。
- 扩展字段至少覆盖：
  - 人工确认点
  - 数据影响
  - 回滚 / 恢复策略

### R-165 默认严格执行模式

- AI 执行任务时默认始终处于严格模式，除非人类明确给出放宽指令；不得因追求速度、省略步骤或压缩表达而丢失需求、约束、证据、历史记录、任务状态或文档同步项。
- 执行过程中必须保留并可追溯：
  - 人类原始要求与补充约束
  - 已确认决策、未确认问题、验证证据与失败记录
  - 任务台账、INBOX、复盘、规则、ADR 与相关权威文档之间的映射关系
- 遇到以下情形时，不得擅自补写为既成事实、默认拍板或静默跳过，必须转由人类决定、批准或补充：
  - 需求、规则、边界、优先级或验收口径不确定
  - 文档、代码、计划或历史记录之间存在冲突
  - 信息缺失且无法从当前仓库事实直接证明
- 修改可能造成语义丢失、历史丢失或兼容性风险
- 对不确定事项的处理顺序固定为：记录影响范围 -> 标注缺口或冲突 -> 进入任务日志、执行计划或 `INBOX.md` -> 等待人类决定后再继续相关变更。

### R-166 临时 AI 交付进度页边界

- 正式业务首页 `/dashboard` 必须保留，不得被“AI 编码进度页”替代或混用。
- 若实现面向架构师/交付负责人的 AI 交付进度页，该页面必须是独立的临时子页面，只服务研发、测试、交付阶段的任务跟踪，不属于 SQLForge 正式产品功能。
- 该页面的展示真值只能来自：
  - `tasks.md`
  - `tasks-done.md`
  - `docs/quality/validation-log.md`
  - 执行计划与 Git / tag 回写记录
- 每次任务新增、修改、执行、阻塞、完成、归档后，必须先更新上述权威来源，再同步页面展示；不得只更新页面而不更新台账。
- 生产环境默认不得展示该页面入口；项目全部结束并投产后，必须隐藏或关闭该页面，但相关历史记录仍需保留在权威台账、验证日志和 Git 中。

### R-167 模块与工程命名禁止追加 Service 后缀

- 模块、目录、Maven `artifactId`、`spring.application.name`、日志默认应用名、运行时标签、客户端标识和服务编码常量等工程命名，不得以 `Service` 作为模块命名后缀。
- 业务语义、产品说明和人类可读文案可以继续使用“XXX服务”表述，但工程命名必须使用去后缀的纯域名，例如 `governance`、`query-execution`、`sqlforge-shared`。
- 本规则不替代后端分层规则；后端实际分层仍以 `controller`、`service`、`domain`、`infrastructure` 为准，`application` 仅作为 `controller`、`service`、`interceptor` 等代码的包域，位于 service 层的具体服务类型继续按职责保留 `*Service` 后缀。
- 历史文档、任务台账、验证日志、规则、计划、脚本和测试在执行该类整改时，必须同步改为当前工程命名，且不得丢失原有章节、步骤、流程、依赖、验证证据和历史语义。
- 仓库必须保留可追溯的旧名到新名映射；后续新增模块或重构批次若发生命名迁移，必须先更新该映射和规则，再推进代码与文档改动。

### R-168 任务收尾上下文收缩与清理

- 每个任务在进入 closeout 前，必须先完成“上下文收缩”，把当前任务执行过程中会影响后续判断的关键信息写回权威来源，至少包括：
  - 已完成范围
  - 验证命令与结果
  - 剩余风险、未决项或人工确认点
  - 下一步与当前任务状态
- “上下文收缩”是结果契约，不绑定某个 Codex 客户端、终端 UI 或斜杠命令；工程规则不得把 `/contract`、`/clear` 一类环境相关命令本身写成唯一必需动作。
- 当前运行环境若支持 `/contract`、`/clear` 或等价命令，可以把它们作为辅助实现手段；若环境不支持，必须以权威台账回写、验证日志、`INBOX.md` / 执行计划补录、重新按 Entry Order 建立上下文等方式完成等价动作，不得因为命令缺失而跳过 closeout。
- 单任务 commit 完成后、切换到下一任务前，必须完成“上下文清理”，确保上一任务的实现细节、临时假设和局部推理不会被静默带入下一任务。
- “上下文清理”后的下一任务必须重新按项目规定的阅读顺序和权威来源建立上下文；不得把上一任务中的未验证记忆直接当作下一任务事实。
