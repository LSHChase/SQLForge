# 多角色体系与权限原则清理影响分析

关联任务：`USER-CN-REMOVE-MULTI-ROLE-PERMISSION-CORE-20260523`

原始需求归档：`docs/references/raw-requirements/USER-CN-REMOVE-MULTI-ROLE-PERMISSION-CORE-20260523.md`

日期：2026-05-23

## 结论

核心产品和核心引擎文档已不再把命名岗位写成目标用户、页面入口或功能差异，也不再保留独立访问原则章节。人类已确认规则文件中本轮新增的岗位体系清理规则也要删除，不保留额外规则条款。

人类已确认继续执行代码级破坏性删除。本轮实现把旧岗位请求头、共享上下文字段、访问矩阵服务、旧内部路径、脚本默认岗位、前端代理岗位参数和相关测试替换为 `tenantId + datasourceId + action` 的非角色化边界；保留跨租户默认拒绝、runtime binding `ACTIVE`、执行留痕、租户隔离、数据源范围和敏感字段加密。

## 已完成清理

- 产品规格：移除目标用户岗位列表，改为按 SQL 查询、解析、推荐、改写、压测、开放接入和系统配置等核心使用场景组织。
- SQL 改写功能边界：移除面向岗位的定位，改为 SQL 改写试算与结果验证流程。
- SQL 改写核心 IR：把人工审核类表述改为人工确认，不再把访问控制写成 DSL 动态配置前置原则。
- 服务能力图：移除角色、权限模型和授权矩阵长期目标，改为租户、数据源范围和执行留痕。
- 接口契约基线：移除旧岗位请求上下文字段和旧岗位请求头文档要求，不再把访问矩阵写成长线接口目标。
- 安全与合规文档：移除角色模型、操作矩阵里的岗位最小角色和权限原则章节，保留身份、租户、数据源范围、只读风险和执行留痕边界。
- 前端设计 / i18n：移除管理员 / 普通用户、岗位页面和访问参数等可见文案。
- 验证脚本：`verify_compliance_baseline.py` 不再用岗位字符串作为合规检查代理。
- 规则和验证：删除本轮新增的岗位体系清理规则与验证段，不在规则文件中保留专门的多角色清理条款。

## 代码与脚本替代结果

本轮代码级替代结果如下：

- `governance` 配置只保留租户到数据源的 `state/actions` 范围，不再维护岗位常量、权限集合或资源矩阵。
- `governance` 内部能力入口保留 `/datasource-access/check` 与 `/datasource-access/scope/change`，语义为数据源范围检查与范围变更，不再暴露旧访问矩阵路径。
- 共享请求上下文保留租户、用户、请求、追踪、认证来源和时间窗，不再携带岗位集合。
- `query-execution`、`sql-optimization`、`benchmark-engine` 的 governance HTTP client 改为调用数据源范围检查。
- smoke、环境脚本、Kafka gate、前端代理和便携前端配置不再发送旧岗位请求头或默认岗位字符串。
- 后端测试和 SDK / JDBC Agent 测试改为构造非角色化受保护请求上下文。
- 告警策略归属从岗位字段调整为数据范围字段。
- 生产规模压测证据中的 `verifierOperator` 属于外部证据操作者字段，不作为产品岗位体系处理；本任务不破坏已归档外部证据格式。

## 已规避的严重后果

本轮替代实现规避了以下风险：

1. 受保护请求头删除旧岗位字段后，`AuthInterceptor`、共享上下文、脚本和测试已同步迁移。
2. 三个业务服务到 governance 的访问决策改为数据源范围检查，不再依赖旧路径。
3. 租户配置、数据源、驱动、元数据和历史访问不再通过岗位判断，避免删除旧矩阵后出现 fail-open。
4. 数据源范围模型继续判断同租户不同数据源是否可用。
5. runtime binding `ACTIVE` 安全约束保留。
6. runtime smoke、Kafka gate、环境 smoke、手工治理 smoke 和单元测试已迁移到新的请求上下文和数据源访问语义。
7. 外部压测证据操作者字段保持兼容，不把外部证据格式纳入本轮破坏性重命名。

## 建议替代方案

推荐方案：删除岗位和权限模型代码，但保留非角色化的执行安全边界。

- 请求上下文保留 `tenantId`、`userId`、`requestId`、`traceId`、`authSource`、`issuedAt`、`expiresAt`；删除旧岗位字段和旧岗位请求头。
- `governance` 删除岗位矩阵，改为租户 + 数据源 + 操作的范围校验；跨租户默认拒绝，不再有平台岗位覆盖。
- 数据源范围只按 `tenantId + datasourceId + action` 判断，不按人群岗位判断。
- 数据源管理、租户配置、驱动上传、元数据全量读取等高风险入口在没有新 owner 模型前默认关闭或仅允许内部服务通道。
- SQL 查询、解析、推荐、改写记录、压测提交按 tenant / datasource 范围和只读 guard 判断，不再按岗位判断。
- 保留审计留痕、敏感字段加密、租户隔离、数据源范围和 runtime binding `ACTIVE`，避免执行链路 fail-open。

## 人类确认结果

`INBOX-008` 已在 2026-05-23 确认：

1. 删除旧岗位请求头、旧岗位上下文字段、岗位常量和访问矩阵配置。
2. 用 `tenantId + datasourceId + action` 替代原访问矩阵，不再按人群岗位判断。
3. 保留 runtime binding `ACTIVE`、租户隔离、数据源范围、执行留痕和敏感字段加密这些非角色化安全边界。
4. 外部证据操作者字段不作为产品岗位体系的一部分破坏性重命名。
