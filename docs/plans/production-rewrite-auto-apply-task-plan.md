# 生产自动改写闭环任务拆解计划

本文把“正常解析/执行后发现并推荐的 SQL，经人类审批后，在后续 SQL 执行时自动改写”的生产闭环拆成多个可由 Codex 独立执行的小任务。

本文只覆盖生产闭环线。投产上线前在本地或测试环境调用生成接口、走通和核验能力的闭环线暂时不纳入本计划。

## 目标闭环

目标生产路径固定为：

1. SQL 解析或执行历史写入。
2. 系统识别可改写候选并生成推荐 SQL。
3. 人类在改写推荐或改写记录上完成审批。
4. 系统完成或复用结果等价验证。
5. 审批通过后，发布动作先调用 `query-execution` runtime binding；只有返回 `ACTIVE` 且绑定 ID / 规则版本可追溯，改写记录才进入 `PUBLISHED`。
6. 后续是否自动替换 SQL 由 query-execution 执行链路命中 active runtime binding 的证据决定，不得仅凭数据库发布状态判断。
7. SQL 执行历史记录原始 SQL、实际执行 SQL、改写来源、规则版本和状态。
8. 周期比对发现差异时先通过 runtime binding 暂停运行时规则，再回写改写记录状态、告警和审计；运行时暂停失败时必须留下失败 trace，不能伪造 `publishStatus=PAUSED`。

## 当前事实基线

- `sql-optimization` 已能在解析/历史写入后触发 `REWRITE` 推荐任务，并能创建 SQL 改写记录、diff 与验证运行记录。
- 推荐中心当前主要是只读入口；推荐本身不是审批状态机。
- 改写记录已有结果验证与周期比对能力；比对失败后的运行时暂停必须走 query-execution runtime binding，`publishStatus=PAUSED` 只能作为 runtime 返回后的本地追踪结果。
- `query-execution` 目前已有“已批准加速绑定”概念，但该路径偏向加速计划选择，不等于 SQL 文本自动改写。
- SQL 执行历史当前有 `rewriteApplied` 等字段，但执行时尚未被生产改写绑定真实驱动。
- JDBC Agent 已有从 Redis 读取改写规则并改写 SQL 的能力，但当前缺少由人类审批后的改写记录发布到运行时规则源的生产管道。
- `manualReviewRequired` 只能表示风险或需要人工复核，不能作为审批通过状态使用；必须新增独立审批状态与发布状态。

## 拆分原则

- 每个任务必须能独立实例化到 `tasks.md`，并通过 `python3 scripts/foreman.py instantiate <TASK_ID>` 开始执行。
- 每个任务只修改一个清晰边界：模型、后端接口、运行时、前端或验证，不混写跨层大改。
- 任务间以明确状态、接口和字段传递，不依赖“页面上看起来能点”作为验收。
- 改写记录生命周期以后端领域状态机和状态接口为入口；发布、暂停和撤销运行时生效必须走 query-execution runtime binding，不能直接改数据库状态绕过绑定链路。
- 所有实现任务必须在开始前重新读取本文、`document-truth-baseline.md`、产品规格、接口基线和相关代码事实，不得只依赖本文摘要。

## 执行顺序

### Wave A：审批与发布语义补齐

先补齐“改写推荐/记录到底在哪里审批、审批后如何进入可发布状态”的数据和服务语义。

### Wave B：运行时自动改写闭环

再把已批准、已验证的改写规则发布到 `query-execution`，并在真实执行路径中自动改写 SQL。

### Wave C：页面与端到端验收

最后补齐页面入口、审计展示、端到端测试和 smoke，避免页面动作与后端真实闭环脱节。

## 任务包

以下 ID 是本文档内的计划 ID，不等同于当前活动任务。进入实现前，需要按仓库治理流程把对应任务 materialize 到 `tasks.md` 或专项 exec plan。

### PRW-001：固化生产改写闭环接口与状态契约

**目标**：在文档和接口契约中明确生产闭环的状态机、服务边界和非目标，防止后续实现再次把“推荐”“人工复核标记”“审批通过”“运行时发布”混为一谈。

**范围**：

- 更新 `docs/architecture/service-interface-contract-baseline.md` 中 `sql-optimization` 与 `query-execution` 的生产改写协作契约。
- 更新 `docs/product/acceleration-rewrite-governance-workbench-spec.md` 中改写审批与自动改写生产闭环说明。
- 不修改业务代码。

**验收**：

- 文档明确区分 `manualReviewRequired`、`reviewStatus`、`publishStatus`。
- 文档说明审批入口在改写记录或推荐详情动作区，而不是加速计划审批页面。
- 文档说明投产前核验闭环暂不纳入本批。
- 执行知识库 lint 或等价文档校验。

### PRW-002：扩展改写记录审批与发布数据模型

**目标**：为改写记录新增独立审批字段、发布字段和运行时绑定追踪字段。

**范围**：

- 数据库增量脚本新增或扩展 `sql_rewrite_record` 字段。
- 后端实体、DTO、MyBatis 映射和仓储读写补齐字段。
- 字段建议包括：
  - `review_status`
  - `review_note`
  - `reviewed_by`
  - `reviewed_at`
  - `publish_status`
  - `runtime_binding_id`
  - `runtime_binding_at`
  - `runtime_binding_by`
  - `runtime_binding_scope`
  - `published_sql_fingerprint`
  - `runtime_rule_version`

**验收**：

- 新字段可创建、查询、更新并在详情接口返回。
- 旧数据有保守默认值，例如 `PENDING_REVIEW` / `UNPUBLISHED`。
- `manualReviewRequired=true` 不会自动变成审批通过。
- 数据库脚本、单元测试和 mapper 测试通过。

### PRW-003：实现改写记录审批状态机

**目标**：新增人类审批动作，使改写记录能从待复核进入批准或驳回状态。

**范围**：

- 在 `sql-optimization` 中新增审批应用服务方法。
- 新增接口，例如 `POST /api/sql-optimization/rewrite-records/{id}/review`。
- 支持 `APPROVED`、`REJECTED`、`CHANGES_REQUESTED` 或仓库既有命名等价状态。
- 写入审批人、审批时间、审批意见、审计 trace。

**验收**：

- 未审批记录不能切换为 `PUBLISHED`。
- 已驳回记录不能发布，除非重新生成或重新进入待审批状态。
- 重复审批、非法状态迁移、缺失审批意见等边界有明确错误响应。
- 控制器测试覆盖成功、非法迁移和权限/上下文缺失场景。

### PRW-004：实现发布资格策略与验证门禁

**目标**：把发布状态参考集中成可测试策略，避免散落在 controller 或页面逻辑里。

**范围**：

- 新增发布资格策略服务，例如 `RewritePublishEligibilityPolicy`。
- 最小门禁：
  - 审批状态为通过。
  - 已存在等价验证通过记录。
  - 推荐 SQL、原始 SQL、SQL 指纹、租户和来源证据完整。
  - 自动应用开关允许。
  - 当前没有未关闭的差异告警或暂停标记。
  - 目标运行时 schema / 方言校验通过。
- 返回结构化拒绝原因，供页面展示。

**验收**：

- 每个门禁均有单元测试。
- 推荐中心只读接口可展示发布资格和拒绝原因，但不得用它阻断状态按钮。

### PRW-005：定义 query-execution 运行时改写绑定模型

**目标**：在 `query-execution` 中建立生产自动改写绑定的内部模型和存储接口，为真实执行路径提供查询能力。

**范围**：

- 新增或扩展运行时绑定对象，至少包含租户、SQL 指纹、原始 SQL 摘要、推荐 SQL、规则版本、发布来源、状态和时间。
- 新增绑定仓储或适配层。
- 状态建议包括 `ACTIVE`、`PAUSED`、`UNPUBLISHED`。
- 不在本任务中改真实 SQL 执行逻辑，只完成绑定模型和基础读写。

**验收**：

- 可创建、查询、暂停、撤销运行时绑定。
- 同租户同指纹的 active 绑定唯一。
- 绑定版本递增或可追踪。
- 仓储测试覆盖唯一性、状态过滤和版本字段。

### PRW-006：实现改写记录发布、暂停和撤销接口

**目标**：把 `sql-optimization` 中已审批、已验证的改写记录发布到 `query-execution` 运行时绑定。

**范围**：

- 新增接口，例如：
  - `POST /api/sql-optimization/rewrite-records/{id}/publish`
  - `POST /api/sql-optimization/rewrite-records/{id}/pause`
  - `POST /api/sql-optimization/rewrite-records/{id}/unpublish`
- `publish` 校验租户、审批状态和发布资格后调用 `query-execution` runtime binding；只有 runtime 返回 `ACTIVE` 后才能把 `publishStatus` 改为 `PUBLISHED`。
- `pause` / `unpublish` 必须调用 `query-execution` runtime binding；只有 runtime 返回 `PAUSED` / `UNPUBLISHED` 后才能回写本地发布状态。
- 回写操作人、时间、原因、runtime binding ID、规则版本和 `lastPublishStatusTrace`；发布资格策略是后端门禁，不只是展示参考。

**验收**：

- 发布成功后改写记录状态为 `PUBLISHED`，且 runtime binding 状态为 `ACTIVE`。
- 暂停或撤销成功后，本地发布状态与 runtime binding 返回状态一致。
- 所有状态动作保留操作人、原因、runtime binding 证据和审计 trace；失败时不能用本地状态改写伪造运行时成功。

### PRW-007：在 query-execution 执行路径应用自动改写

**目标**：让后续同租户、同指纹 SQL 在执行前命中 active 运行时绑定，并自动替换为已批准 SQL。

**范围**：

- 在 `query-execution` 执行入口计算或复用 SQL 指纹。
- 查询 active 改写绑定。
- 命中后以推荐 SQL 作为实际执行 SQL。
- 保留原始 SQL、实际执行 SQL、绑定 ID 和规则版本。
- 未命中或绑定暂停时保持原执行路径。

**验收**：

- 命中绑定时实际执行 SQL 为审批后的推荐 SQL。
- 未命中、租户不匹配、指纹不匹配、绑定暂停时不改写。
- 改写异常时按降级策略执行原 SQL 或失败，行为必须文档化并有测试覆盖。
- 执行历史中 `rewriteApplied=true` 且能追溯绑定来源。

### PRW-008：补齐 SQL 执行历史的改写审计链

**目标**：让 SQL 历史页面和后端历史接口能证明一次执行是否被自动改写、改写前后 SQL 是什么、来源是哪条审批记录。

**范围**：

- 扩展执行历史写入字段或详情 DTO。
- 写入：
  - 原始 SQL。
  - 实际执行 SQL。
  - 是否改写。
  - 改写记录 ID。
  - 运行时绑定 ID。
  - 规则版本。
  - 发布状态快照。
- 对历史查询、详情和导出字段做兼容处理。

**验收**：

- 自动改写执行后，历史详情能完整追溯改写来源。
- 未改写执行不会误标 `rewriteApplied=true`。
- 旧历史记录展示有兼容默认值。
- API 契约测试覆盖历史列表和详情。

### PRW-009：比对差异触发自动暂停与告警闭环

**目标**：周期比对发现改写结果差异时，不只告警，还必须暂停改写记录状态，防止继续被视为可发布状态。

**范围**：

- 扩展现有周期验证服务。
- 当验证结果为不等价或超过容忍阈值时：
  - 更新改写记录 `publishStatus=PAUSED` 或等价状态。
  - 写入告警、trace 和审计事件。
- 不改变正常验证通过路径。

**验收**：

- 差异验证会自动暂停绑定。
- 暂停后后续 SQL 执行不再自动改写。
- 告警中包含改写记录、绑定 ID、规则版本和验证运行 ID。
- 测试覆盖通过、差异、暂停调用失败三类路径。

### PRW-010：推荐中心与改写记录详情页面接入审批动作

**目标**：在页面上给出正确的“人工复核并生效”的入口，避免用户误以为加速计划审批就是 SQL 改写审批。

**范围**：

- 推荐中心详情或改写记录详情增加审批动作区。
- 展示审批状态、发布状态、验证结果、发布资格和拒绝原因。
- 支持审批通过、驳回、发布、暂停、撤销。
- 加速计划审批页面不得被标注为改写审批入口。

**验收**：

- 用户能从推荐 SQL 或 SQL 历史关联记录进入改写复核。
- 审批通过但未发布时，页面明确显示“尚未运行时生效”。
- 发布成功后页面显示绑定 ID、规则版本和生效范围。
- 暂停/撤销后页面状态和后端一致。

### PRW-011：SQL 历史页面展示改写前后链路

**目标**：让运维或审核人员能从一次 SQL 执行历史反查自动改写是否发生、来自哪次审批、是否仍在生效。

**范围**：

- SQL 历史列表增加改写状态筛选或标识。
- SQL 历史详情展示原 SQL、实际执行 SQL、改写 diff、改写记录、运行时绑定和规则版本。
- 提供跳转到改写记录详情的入口。

**验收**：

- 已改写执行可从历史详情跳转到审批记录。
- 未改写执行不会展示误导性发布信息。
- 页面字段来自后端真实审计字段，不由前端推断。

### PRW-012：生产闭环端到端测试与 smoke

**目标**：用测试证明生产路径真的闭合，而不是只证明接口分别存在。

**范围**：

- 后端端到端测试覆盖：
  - 生成改写推荐。
  - 创建或关联改写记录。
  - 审批通过。
  - 验证通过。
  - 发布状态切换为 `PUBLISHED`。
  - 后续执行不因改写记录发布按钮自动触发改写。
  - 历史留痕区分改写记录状态和真实执行改写事实。
  - 差异验证触发暂停。
- 前端 smoke 覆盖审批、发布、历史追溯的关键页面路径。

**验收**：

- 生产闭环 happy path 一次性通过。
- 差异暂停路径一体化通过。
- 测试证据写入任务验证记录。
- 不依赖投产前核验闭环线的接口或页面。

### PRW-013：JDBC Agent Redis 改写规则桥接

**目标**：在主闭环完成后，按需把已发布的生产改写绑定同步到 JDBC Agent 现有 Redis 改写规则格式。

**范围**：

- 新增从运行时绑定到 Redis key 的同步适配。
- 保持 `query-execution` 运行时绑定为生产真值。
- 明确同步失败、过期、撤销和版本覆盖策略。

**验收**：

- 发布后 Redis key 可被 JDBC Agent 读取。
- 暂停或撤销后 Redis key 被删除或标记不可用。
- Redis 同步失败不改变主闭环状态，必须有告警和重试策略。

**执行建议**：本任务为可选后续任务，不应阻塞 PRW-001 到 PRW-012 的生产主闭环。

## 全局验收标准

- 页面上“审核改写并生效”的入口明确存在于改写推荐/改写记录闭环，而不是加速计划审批闭环。
- 审批通过不等于运行时生效；只有发布成功且绑定 active 后才代表后续 SQL 自动改写生效。
- 生产执行路径真实使用批准后的 SQL 执行，并在历史中记录原始 SQL 与实际执行 SQL。
- 周期比对发现差异后，运行时自动改写会被暂停或撤销，不会只停留在告警。
- 所有状态迁移均有后端校验、审计字段、页面展示和测试覆盖。
- 投产前本地/测试环境核验线没有混入本批任务验收口径。

## 非目标

- 不实现投产前核验闭环线。
- 不把加速计划审批改造成 SQL 改写审批。
- 不把 `manualReviewRequired` 当作审批状态。
- 不要求 PRW-001 到 PRW-012 依赖 JDBC Agent 才能闭环。
- 不在本计划中承诺新的物理加速、物化视图或外部执行引擎能力。
